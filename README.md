# SignVerify

전자서명과 해시를 활용한 문서 위변조 검증 서비스 (팀 평문으로말해라)

## 실행

```bash
pip install -r requirements.txt
python app.py
```

브라우저에서 http://127.0.0.1:5000 접속.

## 공격 시나리오 테스트

```bash
python tests/attack_scenarios.py
```

서버를 띄우지 않고 실행되며, 임시 DB를 사용합니다.

## 구조

```
브라우저 (static/app.js, node-forge)            서버 (app.py, Flask + cryptography)        SQLite
───────────────────────────────────            ─────────────────────────────────         ──────
① RSA-2048 키 쌍 생성
   공개키 ─────────────── POST /api/register ─▶ 공개키 형식·길이 확인, 계정과 묶어 저장 ──▶ users
   개인키 → 비밀번호로 AES-256 암호화해 PEM 파일로 저장 (서버로 안 감)

② 문서 SHA-256 → 개인키로 RSA-PSS 서명
   문서+서명+작성자 ─── POST /api/documents ─▶ 해시 재계산 + 공개키로 서명 재검증 ─────▶ documents
                                               (실패하면 저장 거부)

③ 문서번호+파일 ─────── POST /api/verify ────▶ 해시 재계산 + 저장된 서명 검증 ─────────▶ verify_logs
                       ◀── "원본 일치 (작성자)" / "위변조 감지"

④ GET /api/history → 서명·검증 이력
```

| 파일 | 담당 | 내용 |
|---|---|---|
| `static/app.js` | 정호진 | 키 생성, 해시, 서명 (node-forge) |
| `app.py` | 김민재 | API, 공개키 등록, 서명 검증, DB |
| `static/index.html`, `style.css`, `tests/` | 정일재 | 화면, 공격 시나리오 테스트 |

## 설계 포인트 (발표 Q&A 대비)

- **PSS 파라미터를 JS와 Python에서 똑같이 맞춰야 한다.** SHA-256, MGF1(SHA-256), salt 32바이트.
  하나라도 다르면 정상 문서도 검증이 실패한다. (`app.py`의 `PSS_PADDING`, `app.js`의 `PSS_SALT_LENGTH`)
- **왜 PKCS#1 v1.5가 아니라 PSS인가:** PSS는 랜덤 salt를 쓰는 확률적 서명이고 안전성 증명이 있다.
  같은 문서도 서명할 때마다 서명값이 달라진다.
- **서버 측 재검증:** 클라이언트가 계산한 해시나 검증 결과는 믿지 않는다. 서버가 파일 바이트에서 직접
  SHA-256을 계산해 서명과 대조한다.
- **개인키 보관:** localStorage가 아니라 비밀번호로 암호화된 PEM 파일로 사용자 PC에 저장한다.
  XSS가 있어도 암호화된 파일만 노출된다. 서버가 해킹돼도 공개키만 있으므로 서명을 위조할 수 없다.
- **공개키 바꿔치기 방지:** 한 사용자명에는 공개키를 한 번만 등록할 수 있다 (409).
- **문서 제출에 로그인이 필요 없는 이유:** 서명 자체가 개인키를 가진 사람이라는 증명이다.

## 알려진 한계 / 기말까지 할 일

- 최초 공개키 등록 시 본인 확인이 없다 (신뢰의 출발점 문제). 이메일 인증 또는 인증서(CA) 도입 검토.
- 키를 잃어버리면 복구나 교체를 할 수 없다. 비밀번호 확인 후 키를 교체하고 이전 키 이력을 보존하는 기능 필요.
- 비밀번호 해시는 현재 werkzeug(PBKDF2)를 쓴다. 계획대로 bcrypt로 바꿀지 결정해야 한다.
- 서명 시각은 서버 시각이다. 신뢰할 수 있는 타임스탬프(TSA)는 범위 밖이다.
- 검증 화면에서 문서 번호 대신 서명 파일(.sig)로 검증하는 방식도 추가 가능.
